# AgentNotify security audit — 2026-09-19

Scope: the `dev` tree at commit `eb85144` (0.2.0-alpha.3 plus the router/insights split and the new
overview dashboard). Review type: source review of the security-relevant paths, with the code
compiled and rendered on macOS and a direct-plus-transitive dependency vulnerability scan run. No
Windows runtime, no penetration test, and no static analysis were performed (see **Not verified**).

The audit exists because AgentNotify is no longer a purely local notification store: it holds
provider credentials, proxies model traffic, reads agent credential files, and talks to a hosted
Relay service. Each of those is a trust decision worth writing down.

## 1. What the product is trusted with

| Asset | Where it lives | Who can reach it |
| --- | --- | --- |
| Local bearer token (agent API) | `config.json` in the per-user config dir | the OS user, via file modes/ACL |
| Provider/channel secrets (SMTP, Telegram, Slack, Relay installation token, …) | SQLite, encrypted at rest | the OS user; decrypted only in-process |
| Router upstream keys | SQLite, encrypted at rest | the OS user |
| Agent credential files (`~/.claude/.credentials.json`, Codex auth, …) | owned by the agent tools | read-only, in-process, for quota only |
| Notification history, questions, delivery ledger | SQLite | the OS user; the web UI without a sign-in |
| Notification content sent to a channel | leaves the machine | the channel (or the hosted Relay) |

Loopback posture: Kestrel binds `127.0.0.1` only; `/v1` requires a bearer token; `/ui` is
unauthenticated by design but Host/Origin guarded; `/router/*` requires the router key.

## 2. What leaves the machine

This is the part that changed when the app stopped being purely local.

| Flow | Destination | Payload | Protection |
| --- | --- | --- | --- |
| Outbound channel delivery | 19 channel providers | route-redacted notification JSON | TLS; per-provider credentials |
| Relay mobile delivery | `https://an.relay.dev.kabanitech.com` (`src/AgentNotify.Core/Delivery/Channels/RelayChannelAdapter.cs:47`) | notification payload encrypted to each paired device | E2E per-device keys, sender-bound AAD, 24 h envelope expiry |
| Router proxying | the upstream the owner configured | the agent's own request/response bodies | TLS; upstream key attached only to a validated base URL |
| Live quota — Codex | local Codex app-server RPC | no network call by AgentNotify itself | local IPC, agent owns its auth |
| Live quota — Claude Code | `https://api.anthropic.com/api/oauth/usage` | the local OAuth access token as the request credential | TLS, redirects/ambient proxies disabled, token never stored or logged (`SECURITY.md`) |
| Billing (stored API keys) | each provider's official API | the API key | TLS |
| Usage indexing | nowhere | reads local agent logs | read-only, aggregate output |
| Telemetry | nothing | — | no analytics/telemetry code found anywhere in `src` |

## 3. Findings

Severity is about impact if exploited, not about likelihood. "Local" means another process running
as the same OS user, or another user on a shared machine.

### H1 — Secret-protection store can differ per process, and the keychain item can be overwritten (high)

`SecretProtectorFactory.Create` picks the first *usable* key store per process and silently falls back
on any failure (`src/AgentNotify.Core/Delivery/SecretProtectorFactory.cs:41-72`). On macOS the daemon
(GUI session) can read the login keychain while a CLI started from a non-GUI shell cannot; that shell
therefore seals new secrets with `secret.key`, and the daemon can no longer open them. Every delivery
then dead-letters with `provider_secrets_unreadable` while pairing reported success.

The same file makes the ambiguous-error case worse: `MacOsKeychainMasterKeyStore.Find()` collapses
every non-zero exit of `/usr/bin/security` into "no item" (`src/AgentNotify.Core/Delivery/MasterKeyStores.cs:147-152`), so a
transient read failure (`errSecInteractionNotAllowed`) is followed by
`add-generic-password … -U`, which **replaces** the existing key and orphans every envelope sealed
under it. `errSecItemNotFound` and `errSecInteractionNotAllowed` must not be treated alike.

Evidence: `docs/BUG_RELAY_SECRET_KEY_MISMATCH.md` (found 2026-09-15, reproduced, still open) plus the
code paths above. Impact: availability loss and credential re-entry; no remote attacker gains access,
but stored secrets can be made permanently unreadable without a warning.

Fix direction: distinguish "no item" from "cannot read now"; never write when a read failed
ambiguously; persist the chosen store (for example in `config.json`) and reuse it everywhere; make
every entry point log the store it selected, not just the daemon; and surface
`SecretProtection.IsUserBound == false` in the desktop UI, not only in `/ui/api/overview`.

### M1 — Non-keyring fallback key is only as strong as the file mode (medium)

`FileMasterKeyStore` seals provider secrets under `secret.key` and is chosen whenever no keyring is
usable (`src/AgentNotify.Core/Delivery/MasterKeyStores.cs:224-260`). Protection is then file permissions only
(`src/AgentNotify.Core/UnixFilePermissions.cs`, 0700 dir / 0600 file), and those calls are best-effort: failures are swallowed
so the broker always starts (`src/AgentNotify.Core/UnixFilePermissions.cs:56-70`). A config directory on a filesystem
without Unix modes (network share, FAT volume, some container mounts) silently degrades to
world-readable, and `CreateOwnerOnlyDirectory` only tightens the leaf directory, not the parents. The
code reports this honestly through `SecretProtection` ("owner-only key file (weaker than a keyring)").

Fix direction: verify the mode actually applied and warn (or refuse to store new secrets) when it did
not; document that the fallback is not user-bound.

### M2 — The web UI has no authentication, on any machine (medium)

`/ui` trusts whoever can reach the loopback port: no sign-in, and the guard only blocks *web* attacks
(foreign `Host`, missing `X-AgentNotify-UI`, cross-origin `Origin`) — `WebUiEndpoints.Guard`
(`src/AgentNotify.Api/WebUi/WebUiEndpoints.cs:71-113`). Consequences on a shared machine: any other local user can read
notification history and question text, resolve or dismiss notifications, answer an agent's question,
change port/retention/channel settings, upload sounds, and trigger credential-backed probes
(quota/billing refresh, provider test-send). `SECURITY.md` states this trust boundary explicitly, so
it is a documented decision rather than an oversight — but it is worth re-deciding before publishing,
because "other local accounts" is now reachable with a browser and no token.

Fix direction: optional token or OS-keychain-backed unlock for `/ui` on request, or a documented,
first-run acknowledgement; at minimum keep the boundary in the README, not only in `SECURITY.md`.

### M3 — `/ui/api` mutations are not rate limited (medium-low)

The token-bucket limiter applies only to the `/v1` create routes — `POST {root}/notifications`,
`/interactions`, and `/events` (`src/AgentNotify.Api/ApiHost.cs:132-146`) — so no throttle covers `/ui/api`. An
unauthenticated client that can reach the loopback port can therefore loop
`POST /ui/api/quota/refresh` or `/ui/api/billing/refresh`, each of which performs real provider
requests with stored credentials and may trip upstream rate limits on the owner's account.

Size is *not* the gap: every route sits under the global 64 KB cap
(`options.Limits.MaxRequestBodySize = config.MaxRequestBodyBytes`, `src/AgentNotify.Api/ApiHost.cs:77`, default 64 KB in
`AgentNotifyConfig.cs:47`), and the two paths that legitimately need more raise it per request — the
router (32 MB) and the sound upload (10 MB, with an extension allow-list and a sanitized file name).

Fix direction: apply the existing limiter (or a second bucket) to `/ui/api` POST/PUT/DELETE so
credential-backed refresh and test-send routes can only be driven at a bounded rate.

### L1 — The macOS keychain key is passed on the command line (low)

`security add-generic-password … -w <base64 key>` exposes the key in the process table for the
duration of the call (`src/AgentNotify.Core/Delivery/MasterKeyStores.cs:155-163`). Acknowledged in a code comment. Impact is limited
to a same-user observer on a machine where the keychain is already the weaker link.

### L2 — Secrets that stay in plaintext files (low, by design)

`config.json` holds the bearer token, and `AGENTNOTIFY_TOKEN` / `AGENTNOTIFY_PORT` can override it at
startup (`src/AgentNotify.Core/Config/ConfigStore.cs:84-90`). File modes/ACL are the only protection. A same-user process can set
those variables for a broker it launches, or read the file directly.

### L3 — Unauthenticated liveness route (low)

`GET /health` answers without the token (`src/AgentNotify.Api/ApiHost.cs:149`). It returns only `{"status":"ok"}` and no
data, so this is an information-disclosure non-issue unless it is used for local service discovery.
Noted for completeness.

### L4 — Supply chain hygiene (low)

No `Directory.Packages.props`, no `packages.lock.json`, and no automated vulnerability scan in CI.
Direct dependencies are pinned per project (BouncyCastle 2.6.2, MQTTnet 5.2.0.1603, MailKit 4.17.0,
Microsoft.Data.Sqlite 10.0.10, SQLitePCLRaw 2.1.12, ProtectedData 10.0.0). These are exactly the
libraries that handle untrusted protocol data (MQTT, SMTP/MIME, SQLite, crypto).

A one-off scan during this audit (`dotnet package list --vulnerable --include-transitive`, direct and
transitive, against nuget.org, 2026-09-19) reported **no known vulnerable packages** in any of the 11
projects, so there is no outstanding advisory to fix today. The gap is that nothing runs that check
on every change, and a floating transitive resolution can drift between machines and releases.

Fix direction: enable a lock file, centralize versions, and run the vulnerable-package check in CI
before the first public release.

### L5 — Relay metadata exposure (low, product-level)

The Relay payload is end-to-end encrypted to paired devices, and the installation token never reaches
the page (`RelayPairingSessions` remarks). The hosted service still learns the installation identity,
the device set, envelope sizes and timing, and that a delivery happened. Worth stating in the docs
that "local first" means *content*, not metadata, for the mobile path.

## 4. Controls that hold up

- **Local API**: loopback-only listener, bearer token compared in constant time
  (`src/AgentNotify.Api/Auth/TokenAuth.cs:20`), 401 with no detail, token-bucket rate limit on create routes, bounded
  field validation.
- **Secret handling**: DPAPI current-user on Windows; AES-256-GCM under a per-user key elsewhere;
  every API is write-only for secrets — a stored value is never returned (asserted by tests);
  provider summaries carry redacted hints only.
- **Web UI**: exact `Host` allow-list (DNS rebinding), `Origin` must equal that host with no path,
  query, or userinfo, `X-AgentNotify-UI: 1` required on mutations, strict CSP with no
  `unsafe-inline`, `nosniff`, `DENY` framing, `no-store` on API responses.
- **Router**: only `https`, or `http` for the exact loopback literals, and only when the URL has no
  userinfo, query, or fragment (`src/AgentNotify.Router/RouterDestination.cs:20-79`) — the credential is attached only to
  such a URL; inbound router key compared in constant time; ledger tables store wire/model/status/
  token counters and **no prompt or response content** (`src/AgentNotify.Router/RouterRepository.cs:71-105`).
- **Outbound channels**: HTTPS webhook with DNS re-resolution and private-address refusal, opt-in
  private network, no redirect following, forbidden-header list (`src/AgentNotify.Core/Delivery/Channels/WebhookChannelAdapter.cs`).
- **Files**: config written atomically (temp file restricted before rename) and chmod 0600/0700 on
  Unix; sound import sanitizes the file name, caps size at 10 MB, and accepts only `.wav`/`.mp3`.
- **Agent data**: usage indexing returns aggregates and identifiers, never prompt/response text or
  full paths; quota probes never persist or log the OAuth token; the macOS menu-bar child receives
  only the normalized quota projection and no token.
- **Trust hygiene**: no telemetry, analytics, or third-party script in the web UI; a single
  documented trust boundary in `SECURITY.md`.
- **Relay pairing**: the discovery document is fetched from the configured base URL, which must be
  `https` (or consented localhost), and the returned `verification_uri`/`verification_uri_complete`
  must match that base's scheme, host, **and** port before anything is opened or shown
  (`RelayPairingClient.EnsureSameOrigin`, applied at `ChannelSettingsPanel.Relay.cs:73` and
  `RelayPairingSessions.cs:69`). A hostile or impersonated Relay therefore cannot hand back a
  `file:` or custom-scheme URI for the desktop (or WebUI) to launch; a test asserts the rejection
  (`RelayPairingTests.RejectsCrossOriginVerificationUri`). The launched URI is also the only thing
  passed to the browser — no token, code, or credential is placed on a command line.

## 5. Not verified

- No Windows runtime testing: DPAPI behaviour, installer ACLs, and the tray/WebView surface were read,
  not exercised.
- No penetration test, no fuzzing, and no static-analysis/SAST run.
- The dependency scan (L4) covers known *published advisories* only — direct and transitive package
  versions against the NuGet vulnerability database on 2026-09-19. It is not an audit of the
  dependency source.
- GitHub Actions workflows were read for secret handling only; no CI run was executed from this
  machine, and no release artifact was inspected.
- The macOS keychain failure mode behind H1 was read from the code and the existing reproduction note;
  it was not re-triggered against the real login keychain in this pass.
- Multi-user behaviour (another local account reaching `/ui` or `/v1`) was reasoned about from the
  binding and guard code, not tested on a shared machine.

## 6. Suggested order before publishing

1. H1 — make secret-store selection deterministic and shared, and never overwrite an existing key on
   an ambiguous read failure. This is the only finding that silently breaks a working install.
2. M3 — reuse the limiter for `/ui/api` mutations, so credential-backed refreshes are throttled.
3. M2 — decide and document the `/ui` boundary for shared machines (README plus first-run notice, or
   an opt-in token).
4. L4 — add a lock file, centralized versions, and a vulnerability scan to CI.
5. M1 — report when the owner-only modes could not be applied instead of silently continuing.
6. L5 — state the mobile-path metadata caveat ("local first" covers content, not metadata).
